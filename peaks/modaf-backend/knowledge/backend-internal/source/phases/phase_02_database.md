# Phase 2: Database Design

## Purpose

Design and implement the database schema that serves as the foundation for the entire backend. A well-designed schema enforces data integrity at the storage layer, reduces application-level validation burden, and makes future migrations predictable. Every table, column, constraint, and index introduced in this phase must trace back to a requirement identified in Phase 1.

This phase produces the canonical schema file, the initial migration, seed data for all environments, and an entity-relationship diagram (ERD). No application code is written yet -- the goal is a database that could be handed to any developer and understood without reading a single line of backend logic.

---

## Schema Design Process

### Entity Identification from Requirements

Begin by extracting every noun from the requirements that represents something the system must persist. Group them into core entities (direct business objects), supporting entities (lookups, configuration), and junction entities (many-to-many bridges).

Steps:

1. List every resource mentioned in user stories and acceptance criteria.
2. For each resource, determine whether it is truly an independent entity or an attribute of another entity. For example, "address" might be a separate table or a set of columns on `users` depending on whether addresses are shared or reused.
3. Identify implicit entities that requirements assume but do not name explicitly -- audit logs, sessions, tokens, notification records.
4. Assign a preliminary table name to each entity using **plural snake_case** (`users`, `project_members`, `invoice_line_items`).

### Relationship Mapping

Define every relationship between entities and classify it:

- **One-to-One (1:1)**: Rare. Use when splitting a wide table for access-pattern reasons (e.g., `users` and `user_profiles`). Enforce with a UNIQUE constraint on the foreign key column.
- **One-to-Many (1:M)**: The most common relationship. The "many" side holds the foreign key. Example: `projects.id` referenced by `tasks.project_id`.
- **Many-to-Many (M:M)**: Always resolve through a **junction table**. The junction table holds two foreign keys and may carry its own payload columns (e.g., `role` on `project_members`). Name the junction table by combining both entity names in alphabetical order or by choosing a domain-specific name (`project_members` rather than `projects_users`).

Document every relationship in a table:

| Parent | Child / Junction | Type | FK Column | On Delete |
|--------|-----------------|------|-----------|-----------|
| users | projects | 1:M | owner_id | RESTRICT |
| projects | tasks | 1:M | project_id | CASCADE |
| users <-> projects | project_members | M:M | user_id, project_id | CASCADE |

### Column Type Selection

Choose the narrowest correct type for every column. Preferred types:

| Use Case | Type | Rationale |
|----------|------|-----------|
| Primary keys | `uuid` (v4, generated by `gen_random_uuid()`) | Avoids sequential enumeration, safe for distributed inserts |
| Timestamps | `timestamptz` | Always store with timezone; never use `timestamp` without tz |
| Short text with no length constraint | `text` | Prefer over `varchar(n)` unless a hard limit is a business rule |
| Short text with a business-rule limit | `varchar(n)` | Only when the max length is meaningful (e.g., ISO country codes) |
| Structured flexible data | `jsonb` | Searchable, indexable; never use `json` (not indexable) |
| Money / currency | `numeric(12,2)` or `bigint` (cents) | Never use `float` or `double precision` for monetary values |
| Boolean flags | `boolean` with a `DEFAULT` | Always set a default; avoid nullable booleans (three-state logic) |
| Enumerations | `text` with a `CHECK` constraint | Prefer over Postgres `ENUM` type because altering enums requires special migration handling |
| Arrays | `text[]`, `uuid[]` | Use sparingly; prefer junction tables for queryability |

### Constraint Design

Constraints are the schema's immune system. Apply them aggressively:

- **NOT NULL**: Default stance is NOT NULL. Only allow NULL when the absence of a value carries distinct meaning.
- **UNIQUE**: Apply to natural keys, email addresses, slugs, and any column where duplicates would corrupt business logic. For multi-column uniqueness, use a composite unique constraint.
- **CHECK**: Validate value ranges (`CHECK (price >= 0)`), enum-like values (`CHECK (status IN ('draft','active','archived'))`), and string patterns where applicable.
- **Foreign Keys**: Every relationship column must have a foreign key. Specify `ON DELETE` behavior explicitly:
  - `CASCADE` -- when the child has no meaning without the parent (e.g., task comments when a task is deleted).
  - `RESTRICT` -- when deletion of the parent should be blocked if children exist (e.g., deleting a user who owns projects).
  - `SET NULL` -- when the child can exist independently but should lose the association (e.g., assigned_to on a task when the assignee is removed).
- **DEFAULT values**: Provide defaults for `created_at` (`now()`), boolean flags, status columns, and UUIDs (`gen_random_uuid()`).

### Index Strategy

Indexes are not an afterthought. Design them alongside the schema:

- **B-tree indexes** (default): Use for equality lookups (`WHERE status = 'active'`), range queries (`WHERE created_at > '2025-01-01'`), and sorting.
- **GIN indexes**: Use for `jsonb` columns (`CREATE INDEX idx_meta ON table USING gin(meta)`), array columns, and full-text search (`tsvector`).
- **Unique indexes**: Every UNIQUE constraint creates an index implicitly, but you may also create unique partial indexes (`CREATE UNIQUE INDEX idx_active_slug ON pages(slug) WHERE deleted_at IS NULL`).
- **Composite indexes**: Order columns from highest selectivity to lowest. The index on `(tenant_id, created_at)` supports both `WHERE tenant_id = X` and `WHERE tenant_id = X AND created_at > Y`.
- **Foreign key indexes**: Every foreign key column **must** have an index. Postgres does not create these automatically. Missing FK indexes cause full table scans on joins and cascade deletes.
- **Partial indexes**: Use when queries consistently filter on a condition (`WHERE deleted_at IS NULL`). Smaller, faster, and cheaper to maintain.

Rule of thumb: if a column appears in a `WHERE`, `JOIN ON`, or `ORDER BY` clause in any planned query, it needs an index.

## Migration Workflow

### Initial Migration from Schema Design

The first migration creates every table, index, constraint, and function defined in the schema design. Structure it as:

1. Enable required extensions (`uuid-ossp` or `pgcrypto` for UUID generation, `pg_trgm` for trigram search if needed).
2. Create tables in dependency order (parents before children).
3. Create indexes.
4. Create any database functions or triggers (e.g., `updated_at` auto-update trigger).

### Migration Naming Conventions

Every migration file follows the pattern:

```
{timestamp}_{description}.{up|down}.sql
```

Examples:
- `20260326120000_create_users_table.up.sql`
- `20260326120000_create_users_table.down.sql`
- `20260326120100_add_projects_and_tasks.up.sql`

The timestamp is UTC to the second. The description uses snake_case and starts with a verb (`create_`, `add_`, `alter_`, `drop_`, `seed_`).

### Migration Rules

These rules are non-negotiable:

1. **Immutable once applied**: After a migration has run in any shared environment (staging, production), it must never be edited. Create a new migration to make changes.
2. **Always reversible**: Every `up` migration must have a corresponding `down` migration that cleanly undoes it. If a migration cannot be reversed (e.g., dropping a column with data), the `down` migration should raise an explicit error explaining why.
3. **No data loss**: Migrations that remove columns or tables must first verify that the data is either backed up, migrated elsewhere, or confirmed expendable. Add a comment in the migration noting the decision.
4. **Atomic transactions**: Wrap each migration in a transaction (`BEGIN` / `COMMIT`). If any statement fails, the entire migration rolls back.
5. **Idempotent where possible**: Use `IF NOT EXISTS` / `IF EXISTS` guards to prevent errors when a migration is accidentally re-run.
6. **No application logic**: Migrations must not import or depend on application code. They are pure SQL (or a migration tool's DSL).

### Handling Schema Changes Post-Launch

After the application is live and serving traffic:

- **Adding columns**: Always add with a `DEFAULT` value or as `NULL` initially. Backfill data in a separate step, then add the `NOT NULL` constraint in a subsequent migration if needed.
- **Renaming columns**: Never rename directly. Instead: add the new column, backfill, update application code to use the new column, then drop the old column in a later migration.
- **Dropping columns**: First remove all application references, deploy, confirm stability, then create a migration to drop the column.
- **Changing column types**: Create a new column with the target type, migrate data, swap application references, drop the old column.
- **Adding indexes**: Use `CREATE INDEX CONCURRENTLY` in production to avoid locking the table. Note that concurrent index creation cannot run inside a transaction.

## Seeding Strategy

### Dev Seeds (Realistic Sample Data)

Dev seeds populate the local database with enough data to exercise all features:

- Create at least 3 users with different roles (admin, member, viewer).
- Populate every table with at least 5-10 rows.
- Include edge cases: users with no projects, projects with no tasks, tasks with very long descriptions.
- Use realistic-looking data (actual names, plausible dates, varied statuses) rather than "test1", "test2".
- Seed files should be idempotent -- running them twice should not create duplicates. Use `ON CONFLICT DO NOTHING` or check-before-insert logic.

### Test Factories (Deterministic, Isolated)

Test factories are functions that produce database records for automated tests:

- Each factory creates exactly one entity with sensible defaults.
- All values are overridable: `createUser({ role: 'admin' })`.
- Factories handle their own foreign key dependencies -- calling `createTask()` should automatically create a parent project and user if none are provided.
- Data must be deterministic within a test run (use fixed UUIDs or sequential counters, not `gen_random_uuid()` in tests).
- Every test that writes to the database must clean up after itself or run within a transaction that rolls back.

### Production Seeds

Production seeds insert data that the application requires to function:

- System configuration records (feature flags, default settings).
- Admin accounts (with securely hashed passwords, never plaintext).
- Lookup tables (countries, currencies, status definitions) if applicable.
- Permission definitions and role templates.
- Production seeds must be idempotent and safe to run multiple times.

## Common Patterns

### Soft Deletes

Instead of removing rows, set a `deleted_at` column:

```sql
ALTER TABLE tasks ADD COLUMN deleted_at timestamptz DEFAULT NULL;
CREATE INDEX idx_tasks_active ON tasks(id) WHERE deleted_at IS NULL;
```

- All queries must include `WHERE deleted_at IS NULL` by default. Enforce this through application-level default scopes or database views.
- Provide an explicit "purge" mechanism for permanent deletion after a retention period.
- Soft-deleted records should still enforce unique constraints only among active records (use partial unique indexes).

### Audit Timestamps

Every table must include:

```sql
created_at timestamptz NOT NULL DEFAULT now(),
updated_at timestamptz NOT NULL DEFAULT now()
```

Create a reusable trigger to auto-update `updated_at`:

```sql
CREATE OR REPLACE FUNCTION update_updated_at()
RETURNS TRIGGER AS $$
BEGIN
  NEW.updated_at = now();
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER set_updated_at
  BEFORE UPDATE ON your_table
  FOR EACH ROW EXECUTE FUNCTION update_updated_at();
```

Apply this trigger to every table without exception.

### Tenant Isolation

For multi-tenant systems, add a `tenant_id` column to every tenant-scoped table:

- Include `tenant_id` as the first column in all composite indexes.
- Use Row-Level Security (RLS) policies if the database supports it and the application architecture benefits from it.
- Never allow cross-tenant queries in application code. Enforce at the query layer and validate in tests.

### Polymorphic Associations

When multiple entity types can be associated with a single table (e.g., comments on tasks, projects, and documents):

- **Preferred approach**: Use a dedicated foreign key column for each type (`task_id`, `project_id`, `document_id`) with a CHECK constraint ensuring exactly one is non-null.
- **Alternative**: Use `commentable_type` + `commentable_id` columns. This pattern sacrifices foreign key enforcement for flexibility. If used, add application-level validation and document the trade-off.
- Avoid polymorphic associations when possible. Separate junction tables are almost always cleaner.

## Deliverables

| Deliverable | Description |
|-------------|-------------|
| **Schema file** | A single SQL file (or set of files) that defines every table, column, constraint, index, trigger, and function. This is the source of truth. |
| **Initial migration** | The `up` and `down` migration files that create (and destroy) the entire schema. |
| **Seed files** | Separate seed files for dev, test factories, and production. Each clearly labeled and idempotent. |
| **ERD** | An entity-relationship diagram showing all tables, columns (with types), primary keys, foreign keys, and relationship cardinality. Generate from the schema file using a tool or maintain manually. |

---

## Validation Gate

This phase is complete when all of the following are true:

- [ ] The initial migration runs cleanly from an empty database without errors.
- [ ] The `down` migration drops everything and the `up` migration can run again (roundtrip test).
- [ ] Dev seeds populate all tables with realistic data.
- [ ] Test factories can create any entity in isolation.
- [ ] Production seeds insert required configuration data.
- [ ] Every foreign key column has a corresponding index.
- [ ] No `timestamp` columns exist without timezone (`timestamptz` only).
- [ ] Every table has `created_at` and `updated_at` columns with the auto-update trigger.
- [ ] The ERD matches the schema file exactly.
- [ ] A peer review has confirmed that the schema matches Phase 1 requirements with no missing entities or relationships.
- [ ] No column is nullable without a documented reason.
- [ ] All CHECK constraints have been tested with invalid data to confirm they reject correctly.
